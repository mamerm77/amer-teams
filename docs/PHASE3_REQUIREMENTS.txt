Amer Teams — Consolidated Requirements (Single Phase)

Nov 19, 2026 · @Moh Amer

Summary

Amer Teams already matches competitors on encrypted chat, calls,
meetings, scheduling and a basic co-pilot. It goes beyond them in three
places: post-quantum call keys, real-telemetry operations and Agent Ops.
The biggest gaps are AI that acts across the workspace, structured
collaboration (canvases, loops, workflows), large events, and external
collaboration.

The competition moved in 2026 from "AI that summarises" to "AI agents
that do the work". In March 2026 Salesforce launched more than 30 new AI
features for Slackbot, positioning Slack as an agentic workflow platform
(source). Zoom repositioned Workplace with AI Companion 3.0, workflow
automation and custom AI agents (source). Microsoft Teams added
interactive Copilot agents inside meetings and AI catch-up summaries for
chats (source).

Amer Teams' winning position: the only collaboration suite where every
agent is encrypted end-to-end, observable live, and accountable. Every
creative feature below builds on that.

Top 5 to build first:

1.  Catch-up digest and an agent you can talk to inside a meeting
    (closes the biggest AI gap)

2.  Workflows: no-code automations driven by plain language

3.  Shared live canvases attached to chats and meetings

4.  Secure external collaboration between organisations

5.  Agent Ops for everyone: a personal agent team per user, shown live

Scope of this phase

This document holds every requirement agreed for Amer Teams in this
round, delivered in one phase (Phase 3, about 6 months):

1.  Agent Ops: an AI agent team that delivers any project, with a live
    interface that shows the agents' real status. Built first; see
    below.

2.  Competitor parity: 20 features from Teams, Slack, Zoom, Google Meet
    and Webex.

3.  Creative features: 15 features unique to Amer Teams.

4.  Practical features: 25 everyday features.

5.  Logic and detailed specs for every feature.

6.  Modern 3D UI across the app, with 2.5D and flat fallbacks.

Three rules keep a single phase safe:

1.  Foundations first, in weeks 1 to 4: the agent event bus, the private
    agent messages, the permission model for cross-organisation channels
    and the enclave research spike. Every workstream builds on these.

2.  Feature flags per tenant: every feature merges to main continuously
    but switches on only after its tests pass, so one late feature never
    blocks the release.

3.  One gate at month 6: all 60 features pass automated tests on the
    live test servers, and a pilot group of 50 users runs on them for 2
    weeks with no severity-1 issues.

The main risk is team size. With today's team of one or two developers
plus agents, the same scope takes 15 to 18 months. The Agent Ops team
can carry part of the coding and testing load, but it should be measured
on the first features before the plan counts on it.

Feature logic

How each Phase 3 feature works: what triggers it, the steps the system
runs, the data and API it adds to the existing orchestrator and Flutter
app, and the rules that guard it. API paths sit under the orchestrator's
/v1 prefix; every action by an agent is written to the hash-chained
audit log and streamed to Agent Ops.

AI and agents

Catch-up digest

-   Trigger: user opens the app after 4+ hours away, or taps "Catch me
    up".

-   Logic: 1) client collects unread messages per room since
    last_read; 2) decrypts them on device; 3) ranks rooms by mentions,
    direct messages, then priority senders; 4) sends the top 30 threads
    to the summariser (on-device model if available, else the enclave,
    never plain server); 5) returns one card per room: 2-line summary,
    decisions, items needing reply, with deep links.

-   Data/API: POST /ai/digest {rooms[], window}; cache the digest per
    user for 30 min.

-   Guards: rooms labelled Confidential are listed by name only; mute
    and quiet-hours settings respected.

Ask-the-meeting agent

-   Trigger: /ask in the meeting chat, or the Amer button in a call.

-   Logic: 1) live captions (already on device) stream to an encrypted
    rolling transcript buffer; 2) the question plus the last 20 minutes
    of transcript and shared slide text go to the co-pilot; 3) the
    answer posts as a private agent message to the asker only, with
    "share to everyone".

-   Data/API: POST /meetings/{call_id}/ask; transcript buffer held in
    memory, deleted at call end unless minutes are on.

-   Guards: works only if the host enabled AI for the meeting; every
    participant sees an "AI listening" badge.

Video recap

-   Trigger: recorded meeting ends.

-   Logic: 1) transcript is split into topics by the minutes agent; 2)
    each topic gets a title, start/end time and 1-line summary; 3) the 3
    to 5 key moments are cut as clips; 4) recap card posts to the
    meeting chat.

-   Data/API: recap_chapters(call_id, start_s, end_s, title, summary);
    GET /meetings/{id}/recap.

-   Guards: inherits the recording's retention and sensitivity label.

AI skills and custom agents

-   Trigger: user saves a prompt as a skill, or builds an agent in the
    Agent Builder.

-   Logic: skill = name, instructions, allowed tools, input fields;
    agent = skill set + model + schedule. On run, Guardian checks the
    caller's rights, the agent runs through the Agent Ops runner, and
    every step streams to Agent Ops.

-   Data/API: skills, custom_agents tables; POST /agents/custom, POST
    /agents/{id}/run.

-   Guards: tools limited to an allow-list per role; admin approval
    before an agent is shared org-wide.

In-person meeting notes

-   Trigger: "Take notes" on a phone in a physical room.

-   Logic: on-device speech-to-text, speaker separation, then the
    minutes agent produces minutes and action items into the linked
    calendar event's chat.

-   Guards: a visible banner and a spoken consent prompt; audio never
    leaves the phone.

Personal agent team

-   Trigger: user assigns a goal ("prepare the vendor comparison for
    Sunday").

-   Logic: creates an Agent Ops project scoped to the user's own data;
    orchestrator plans, delegates to researcher, writer and scheduler;
    progress is shown live; deliverables land in the user's Saved area.

-   Data/API: reuse /agentops/projects with owner and scope=personal;
    per-user monthly token budget.

-   Guards: agent reads only rooms the user can read; any outbound
    action goes through the glass box.

Agent glass box

-   Trigger: any agent action that sends, books, deletes, shares or
    spends.

-   Logic: 1) agent's PreToolUse hook pauses the action; 2) a card shows
    plan, data touched, recipients and cost estimate; 3) user approves,
    edits or rejects; 4) decision is audited and the agent resumes or
    stops.

-   Data/API: agent_approvals(id, project_id, action, payload_hash,
    status, decided_by); POST /agentops/approvals/{id}.

-   Guards: timeout after 24 h counts as rejected; read-only actions
    skip the card.

Pre-mortem agent

-   Trigger: a message tagged #decision, or /premortem.

-   Logic: agent gathers the thread and linked files, writes the
    strongest case against the proposal, the top 3 risks with likelihood
    and impact, and what would change its mind. Posts as a reply.

-   Guards: labelled clearly as a devil's-advocate view; one run per
    decision unless asked again.

Organisation agent marketplace

-   Trigger: a team publishes a custom agent.

-   Logic: submission → automated tests (sample prompts, tool policy
    check) → admin approval → listed with owner, version, rating and
    live usage from Agent Ops. Install = grant the agent to a team or
    user.

-   Data/API: agent_listings, agent_installs; GET /marketplace, POST
    /marketplace/{id}/install.

-   Guards: each version is pinned; an update needs re-approval; usage
    and errors visible to the owner.

Decision ledger

-   Trigger: the minutes agent or a chat detector spots decision
    language, or a user marks a message as a decision.

-   Logic: 1) proposes {decision, owner, due date, source link}; 2)
    participants confirm with one tap; 3) confirmed entry is
    hash-chained like the audit log; 4) reminders before the due
    date; 5) changes create a new version, never overwrite.

-   Data/API: decisions(id, room_hash, text, owner, due, status,
    prev_hash, hash); GET /decisions?owner=.

-   Guards: only confirmed decisions enter the ledger; text stays
    encrypted, the server keeps only the hash and metadata.

Meeting digital twin

-   Trigger: "Open replay" on any recorded meeting.

-   Logic: combines transcript, speaker timeline, chapters, decisions
    and call-quality trace into one interactive view; "ask the meeting"
    uses the full transcript.

-   Guards: same access as the recording.

Live expertise map

-   Trigger: search "who knows about X".

-   Logic: each client builds topic tags from its own decrypted messages
    and publishes only the tags (not content) to the directory, opt-in;
    the search ranks people by tag weight and recency.

-   Data/API: expertise_tags(user, tag, weight, updated); GET
    /people/experts?q=.

-   Guards: opt-in per user; tags can be reviewed and removed; nothing
    from private chats unless the user allows.

Encrypted AI and security

Encrypted AI (on device and in enclaves)

-   Trigger: any AI request on encrypted content.

-   Logic: 1) router checks device capability; small tasks (translation,
    short summaries) run on an on-device model; 2) larger tasks go to an
    inference service inside a confidential-computing enclave; 3) the
    client verifies the enclave's attestation report before sending; 4)
    content is encrypted to the enclave's key, processed, answer
    returned encrypted, nothing stored.

-   Data/API: GET /ai/enclave/attestation; POST /ai/enclave/infer
    (ciphertext only).

-   Guards: if attestation fails, the request is refused, never silently
    sent in plain text; a lock icon shows where the AI ran.

Quantum-safe badge

-   Trigger: opening any chat or call.

-   Logic: shows key type (Megolm for chat; ML-KEM-768 + X25519 hybrid
    for calls), last key rotation time and the safety code. Tap for
    details. Turns amber if any participant's device is unverified, red
    if a downgrade is detected.

-   Data/API: read from pq_service and the call key events already in
    the app.

-   Guards: a downgrade blocks the call until the user accepts the risk.

Deepfake and impersonation detection

-   Trigger: a participant joins a call or a voice message arrives.

-   Logic: 1) the receiving device runs a liveness and synthetic-voice
    classifier on the decrypted stream; 2) it checks the speaker against
    the verified device keys of the claimed user; 3) a risk score above
    the threshold shows a warning to that viewer only.

-   Guards: detection runs on device to keep E2EE; warnings say
    "possible", never accuse; false-positive reports feed tuning.

Data-loss prevention and sensitivity labels

-   Trigger: sending a message or file, or starting a recording.

-   Logic: 1) client classifies content against tenant rules (card
    numbers, national IDs, keywords, file labels); 2) actions: warn,
    require a reason, or block; 3) labels propagate to recordings,
    minutes, transcripts and AI outputs; 4) Guardian already blocks AI
    on Confidential labels.

-   Data/API: dlp_rules(tenant, pattern, action), pushed to clients;
    POST /dlp/events (metadata only).

-   Guards: scanning happens on the device, so the server still never
    sees content.

Retention and auto-delete timers

-   Trigger: owner sets a timer on a chat (1 day to 7 years) or the
    tenant sets a policy.

-   Logic: timer is stored in room state; each client deletes expired
    messages locally; the server redacts expired events and deletes
    media; tenant policy wins over a shorter user timer only when
    compliance is on.

-   Guards: a banner shows the active timer; legal hold pauses deletion.

Guest accounts

-   Trigger: an admin or allowed member invites an external email.

-   Logic: creates a Matrix account flagged guest with an expiry

Common rules

  -----------------------------------------------------------------------
  Rule                 Specification
  -------------------- --------------------------------------------------
  Request lifecycle    Every long action is a job: queued → running →
                       succeeded / failed / cancelled. Job id returned at
                       once (HTTP 202); progress streamed over the
                       existing SSE channel.

  Idempotency          Every POST that creates something accepts
                       Idempotency-Key; a repeat within 24 h returns the
                       first result.

  Retries              Network and 5xx errors: 3 retries, exponential
                       back-off 1 s, 4 s, 16 s with jitter. 4xx: never
                       retried. LLM overload (429/529): retry up to 5
                       times, then fail with a clear message.

  Timeouts             API calls 10 s; AI calls 60 s (streamed); agent
                       jobs bounded by turn and token budgets, not wall
                       time.

  Limits               Per user: 60 AI requests per hour, 3 concurrent
                       agent jobs, monthly token budget set by the
                       tenant. Per tenant: configurable caps; 80%
                       warning, 100% hard stop.

  Permissions          Checked on the server for every call: Matrix
                       membership for room data, require_admin for admin,
                       role allow-lists for agent tools. Clients never
                       decide access.

  Encryption           Content is decrypted only on members' devices or
                       in an attested enclave. The server stores
                       ciphertext, hashes and metadata.

  Audit                Every create, change, delete, approval and agent
                       action writes to the hash-chained audit_log with
                       actor, action and object id.

  Telemetry            Prometheus counters for requests, errors and

  Localisation         All strings in ARB files, Arabic and English from

  Tests                Each feature ships with unit tests, an API test, a

Agent glass box and personal agent team

State machine of an agent action

proposed → awaiting_approval → approved → executing → done, with exits
rejected, edited → awaiting_approval, expired (24 h), failed. Read-only
actions go proposed → executing directly.

Sequence

1.  The agent calls a tool. The PreToolUse hook classifies it: read,
    write-internal (own drafts), write-external (send, book, share,
    delete, spend).

2.  Read and write-internal run at once. Write-external creates an
    agent_approvals row, emits approval.requested to Agent Ops and
    pushes a notification to the owner.

3.  The hook returns permissionDecision: "ask" and the SDK session waits
    (the runner keeps the session; nothing is lost).

4.  The user opens the card: plan (agent's own one-line reason), target
    (people, rooms, systems), a diff or preview of what will be sent,
    data touched, estimated tokens and money.

5.  Approve → hook returns allow, the tool runs, the result is audited.
    Edit → the edited payload replaces the original and its hash is
    stored. Reject → the agent receives "rejected by user: <reason>" and
    must re-plan.

6.  The project's stream shows every step; the owner can pause or stop
    the whole team at any time.

Acceptance tests

-   An agent tries to send a message: no message is delivered until
    approval; rejecting it delivers nothing.

-   Editing the text changes what is sent and the audit log stores the
    edited hash.

-   A personal agent cannot read a room the owner is not in (403 from
    Synapse surfaces as a tool error).

-   At 100% budget, no further model calls are made.

Catch-up digest and ask-the-meeting

Catch-up digest: sequence

1.  Client computes the away window: now - max(last_active, 4 h ago);
    manual tap uses "since last digest".

2.  Collects unread events from the local store per room; skips muted
    rooms and rooms in quiet mode.

3.  Scores each room: score = 5·mentions + 4·direct +
    3·priority_sender + 2·questions_to_me + 1·log(unread).

4.  Takes the top 30 rooms, max 200 messages each (newest first), strips
    media to captions.

5.  Labels: Confidential rooms → title only; Restricted → on-device
    model only.

6.  Router (see Encrypted AI) chooses device or enclave; prompt asks for
    JSON {room_id, summary (≤30 words), decisions[], asks_for_me[],
    deadlines[]}.

7.  Validates the JSON against a schema; on failure retries once, then
    falls back to "N unread, M mentions".

8.  Renders cards in score order; tapping a card jumps to the first
    unread message. Marks rooms as "digested", not as read.

Limits: one automatic digest per 4 h; enclave input capped at 60k
tokens; digest cached locally for 30 min, never on the server.

Acceptance tests: a mention ranks its room first; muted rooms never
appear; a Confidential room shows no summary text; malformed model
output falls back to counts.

Ask-the-meeting: sequence

1.  Host enables "AI in this meeting"; every participant gets the badge
    and a one-time notice.

2.  Each participant's device produces captions for the audio it hears;
    the host's device keeps a rolling transcript (speaker, time, text)
    for the last 60 minutes in memory.

3.  A question via /ask or the Amer button goes to the host device's
    agent bridge with transcript and shared-slide text (OCR on device).

4.  Answer is returned as a private agent message to the asker, with
    timestamps cited; "Share" posts it to the meeting chat.

5.  At call end, the buffer is wiped unless minutes are on, in which
    case it becomes the minutes input.

Failure cases: host leaves → transcript role moves to the next
participant with AI allowed; a question about a time before the buffer →
"I only have the last 60 minutes".

Acceptance tests: with AI disabled, /ask returns "AI is off for this
meeting"; answers cite at least one timestamp; no transcript text
reaches the server's database.

Decision ledger and tasks

Decision states: detected → proposed → confirmed → (in_progress) → done
| superseded | cancelled. A detected decision that nobody confirms
within 72 h is dropped.

Detection logic

1.  Sources: minutes agent output, chat messages matching decision
    phrases ("we agreed", "decided", "go with", Arabic "تم الاتفاق",
    "قررنا"), or a manual "Mark as decision".

2.  The agent extracts {text, owner, due, options_rejected[]} and posts
    a proposal card in the room.

3.  Confirmation: the owner plus at least one other participant tap
    Confirm (configurable quorum).

4.  On confirm, the client sends an encrypted room event with the full
    text; the server stores only metadata and a hash chain entry.

5.  A change creates a new version linked to the previous one; the old
    version is shown as superseded.

CREATE TABLE decisions (
id text PRIMARY KEY, room_hash text NOT NULL, event_id text NOT NULL,
owner text NOT NULL, due date, status text NOT NULL,
version int NOT NULL DEFAULT 1, supersedes text,
confirmed_by text[] NOT NULL, prev_hash text NOT NULL, hash text NOT
NULL,
created_at timestamptz NOT NULL DEFAULT now());

Tasks

-   Event com.amerteams.task {title, owner, due, status, source_event};
    updates are new events referencing the task id (latest wins by
    origin time).

-   States: open → in_progress → done, plus blocked with a reason.

-   Reminders: local notifications 24 h and 1 h before due; overdue
    tasks appear at the top of the personal board.

-   A decision with an owner and due date creates a linked task

Acceptance tests: a decision needs the quorum before it appears in the
ledger; editing creates version 2 and keeps version 1 visible; tampering

Plain-language workflows

Definition format (stored as JSON, versioned)

{"name": "RFP quote approval",
"trigger": {"type": "message", "room": "#rfp", "match": {"has_file":
true, "keywords": ["quote"]}},
"steps": [
{"id": "s1", "type": "ask_form", "to": "$trigger.sender", "fields":
["vendor", "amount_aed"]},
{"id": "s2", "type": "condition", "if": "$s1.amount_aed > 500000",
"then": "s3", "else": "s4"},
{"id": "s3", "type": "approval", "approvers": ["role:finance_manager"],
"timeout_h": 48},
{"id": "s4", "type": "post", "room": "#rfp-log", "text": "Quote from
{{s1.vendor}} logged"}]}

Trigger types: message, schedule (cron), webhook, form submitted, alarm,
calendar event, manual. Step types: post, ask_form, approval, condition,
wait, call_connector, run_agent, create_task, http (admin-approved hosts
only).

Build sequence

1.  The user describes the workflow; the workflow agent returns a
    definition plus a list of assumptions.

2.  The definition is validated: known step types, reachable steps, no
    cycles without a wait, every referenced room and role exists, the
    creator has rights on every room.

3.  The app shows it as a visual flow; the user edits and runs a dry-run
    with sample data (no side effects).

4.  Save creates version N; enable starts listening for the trigger.

Run sequence

1.  Trigger fires → a workflow_runs row with the trigger payload.

2.  Steps execute in order; each step's result is stored and available
    as $step.field.

3.  Approval and form steps pause the run; timeouts follow the step's
    on_timeout (default: fail).

4.  Failures retry 3 times, then the run fails and the owner is notified
    with the failing step.

5.  Every step streams to Agent Ops and the audit log.

CREATE TABLE workflows (id text PRIMARY KEY, owner text, tenant text,
name text,
version int, definition jsonb, enabled boolean, created_at timestamptz);
CREATE TABLE workflow_runs (id text PRIMARY KEY, workflow_id text,
version int,
status text, trigger jsonb, step_results jsonb, started_at timestamptz,
ended_at timestamptz);

Where steps run: steps that read encrypted messages run on the owner's
device (a workflow runner in the app, active when the device is online)
or in the enclave; metadata-only steps run on the server.

Limits: 50 steps per workflow, 1,000 runs per day per workflow, run time
30 days maximum (for long approvals).

Acceptance tests: a cycle without a wait is rejected at save; a dry-run
sends nothing; a workflow cannot post into a room its owner has left; a
changed definition does not affect runs already in progress.

Enclave sequence

1.  Client fetches GET /ai/enclave/attestation: report signed by the
    hardware vendor, measurement of the enclave image, its public key.

2.  Client checks the signature chain, that the measurement matches the
    published build hash (pinned in the app), and the report is under 24
    h old.

3.  Client creates a one-time key, encrypts the request with the enclave
    key (HPKE), sends POST /ai/enclave/infer.

4.  Inside the enclave, the request is decrypted, sent to the model over
    an attested TLS link, the answer is encrypted to the client's
    one-time key.

5.  The enclave keeps nothing: no logs of content, only token counts and
    timing for billing.

Deployment options: confidential VMs (AMD SEV-SNP or Intel TDX) in a UAE
cloud region running a pinned inference proxy; GPU confidential
computing for self-hosted models when available.

Acceptance tests: a tampered attestation is refused; Restricted content
never leaves the device (verified by network capture in CI); enclave
logs contain no message text; when the enclave is down, no plain-text
request is ever made.

Canvases, shared channels, webinars, network-aware calls, operator mode

Canvases

-   Model: one Yjs document per canvas; each update is a binary delta
    wrapped in an encrypted event com.amerteams.canvas.update
    {canvas_id, delta}. Every 200 updates, a member posts a snapshot
    event so new joiners load fast.

-   Merge: CRDT guarantees all members converge regardless of order; no
    server merge.

-   Presence: cursors and selections are sent as ephemeral to-device
    messages, never stored.

-   Limits: 5 MB per canvas snapshot; images stored as encrypted media
    and referenced.

-   Tests: two offline edits to the same paragraph converge on
    reconnect; a removed member cannot decrypt new updates.

Shared channels across organisations

-   Connection states: requested → approved_by_us → approved_by_both →
    active → suspended | disconnected.

-   Logic: approval on both sides adds each server to the other's
    Synapse federation allow-list; room creation sets m.federate: true
    only for rooms marked shared; each server's policy hook checks
    outgoing events against its own DLP rules.

-   Disconnect: removes the partner from the allow-list; rooms remain
    readable to local members with history up to the disconnect.

-   Tests: a non-approved server cannot join; DLP on side A blocks a
    card number before it leaves A.

Webinars and town halls

-   States: draft → scheduled → live → ended → archived.

-   Scale path: up to 300 viewers through LiveKit directly; above that,
    an egress worker composites the presenters and publishes LL-HLS
    through a CDN with 3 to 5 s latency.

-   Q&A: questions are events in a moderated side room; upvotes as
    reactions; moderators promote to "on screen".

-   Registration: registrations(event_id, email, token, attended,
    joined_at, left_at); tokens single-use per device.

-   Tests: an attendee token cannot publish media; attendance report
    counts match LiveKit participant logs.

Network-aware calls

-   Inputs every 2 s: RTT, packet loss, jitter, available bitrate,
    network type (Wi-Fi, 4G, 5G).

-   Forecast: exponentially weighted moving average plus trend over the
    last 10 samples; predicted loss above 3% or RTT above 300 ms counts
    as "degrading".

-   Actions in order: lower video layer → switch to audio-priority mode
    → move to the nearest media node (if multiple LiveKit regions) →
    suggest audio-only. Each action holds at least 10 s to avoid
    flapping.

-   Tests: a simulated 5% loss triggers a step-down within 4 s; quality
    recovers by step-up after 20 s of good samples.

Operator mode for telecoms

-   Correlation: alarms grouped when they share a site or a link within
    a 5-minute window; severity = highest in the group; one incident per
    group.

-   Incident states: open → acknowledged → mitigating → resolved →
    reviewed.

-   Automation: open → create channel, invite on-call (from rota), start
    bridge, post topology snippet and last 24 h of changes; resolved →
    agent drafts the report (timeline, impact, root cause, actions) for
    the incident owner to approve.

-   Guards: network element actions are suggestions only; execution
    needs a named engineer's approval in the glass box.

-   Tests: 20 alarms from one site within 5 minutes create one incident;
    the report draft contains every timeline entry.

3D UI

A modern 3D interface for Amer Teams that stays fast on mid-range
phones, readable in Arabic and English, and accessible.

Design principles

1.  Depth shows meaning, not decoration. Layers in Z express hierarchy:
    active call above chat, chat above the list, the Amer avatar above
    everything when it speaks.

2.  3D where it explains, flat where people read. Message text, forms
    and tables stay flat and sharp; 3D is used for spaces, people,
    agents, networks and transitions.

3.  Calm by default. Motion only on state change; idle scenes are still.
    A "Reduce motion" setting flattens everything.

4.  Fast on a mid-range phone. 60 fps target, 3D scenes capped at 4 ms
    GPU per frame; anything slower falls back to 2.5D.

5.  Right-to-left aware. Scenes mirror for Arabic: the camera, light
    direction and list flow all follow reading direction.

Interaction rules

-   Every 3D element has a 2D tap target of at least 48 dp.

-   Gestures are optional shortcuts; every action is also reachable
    through a visible button.

-   Camera moves are always user-initiated, except for a gentle
    re-centre after 5 seconds of inactivity.

-   Haptics: light tick on lift, medium on confirm, none during calls.

Accessibility

-   Reduce motion and the system "remove animations" setting switch all
    views to flat.

-   Screen readers get a semantic tree for 3D scenes (each agent,
    participant or site is a labelled node with its state).

-   Contrast ratio of at least 4.5:1 for text on glass, enforced by a
    darker scrim behind text.

-   No information is carried by depth or colour alone; every state has
    a text label.

Build plan inside the single phase

1.  Weeks 1–3: design tokens (depth levels, glass, light, motion) in
    theme.dart; a Depth widget and GlassPanel component; GPU-tier
    detection and the fallback switch.

2.  Weeks 3–8: 2.5D pass on every screen (home, chat list, chat, calls,
    settings).

3.  Weeks 6–14: real 3D scenes: Agent Ops graph, calls semicircle, Amer
    avatar with lip-sync.

4.  Weeks 12–20: immersive meetings, presence rooms, operator mode map,
    health pillars.

5.  Weeks 18–24: performance tuning on low-end Android, Arabic mirroring
    review, accessibility audit, golden-image tests for every view in
    all three modes (3D, 2.5D, flat).

Acceptance tests: 60 fps on the reference mid-range phone in every 3D
view; every screen passes the screen-reader audit; switching Reduce
motion on changes every view to flat within one frame; Arabic layouts
mirror correctly in golden tests.
